# EVO：记忆的 CI

### 一个零依赖、可审计的 Agent 经验账本

**版本** v1.0 · 对应当前实现 `v0.21` / Skill 协议 `v1.3`
**协议** AGPL-3.0-or-later（`data/` 判据层另有商业授权）
**平台** 纯 POSIX shell + mawk，无任何运行时依赖

---

## 摘要

2026 年，Agent 记忆已经是成熟赛道。Mem0 做托管记忆 API，Zep 做时序知识图谱，Letta 做 OS 式记忆管理，LangMem 做模块化记忆。它们解决的是同一个问题：**该记住什么、该调出什么**。

但生产环境里还有第二个问题，没有人正面回答：

> **我记下来的这些东西，到底还对不对？**

记忆库会污染（录入了错误结论）、会退化（早期好条目被后期噪音淹没）、会不可审计（三周后你无法解释为什么当时那么判断）、会不可复现（换个模型、换次运行，检索结果就变了）。

EVO 只做第二件事。

它不提供嵌入模型，不提供向量库，不提供托管服务。它是一个 **63 条经验的明文账本**，加一套 **19 项结构检查 / 41 条自检断言 / 32 条对抗用例** 的门禁，加一个 **账本口径的检索基准**。

用一句话说：**EVO 是记忆层的 CI。**

`git` 给了记忆版本化，`CI` 给了记忆质量门禁。市面上的记忆方案全都有前者的一部分，没有一家有后者。

## 1. 问题：AI 助手的记忆为什么不可信

### 1.1 上下文窗口不是记忆

窗口再大，每轮对话结束记忆就清零。Agent 记不住用户偏好、记不住昨天的半成品、记不住上个工单的处理结论。这是共识，不用论证。

真正被忽略的是下一层：**记忆一旦跨会话持久化，它就变成了一个需要被维护的数据集**，而数据集会腐烂。

### 1.2 四种失败模式

| 失败模式 | 表现 | 现有方案怎么处理 |
|---|---|---|
| **遗忘** | 该记的没记下来 | 各家都在解（自动提取、写入策略） |
| **污染** | 记了错的、记了噪音、新旧事实矛盾 | 部分在解（Zep 的 `valid_at/invalid_at` 最结构化） |
| **退化** | 库越写越乱，早期好条目被淹没，检索质量逐月下降 | **基本无人处理** |
| **不可审计** | 无法回答"为什么当时这么判断"、无法复现 | **基本无人处理** |

后两项是本文的靶心。

### 1.3 为什么退化是致命的

一个自动提取型记忆系统，在理想条件下每条新记忆都是增益。但实际上：

- 写入没有准入门槛 → 噪音持续注入
- 噪音参与检索竞争 → 好条目的排名被挤下去
- **没有任何机制告诉你排名下降了**

这就是**静默劣化**：系统不会报错，不会崩溃，只是越来越不靠谱。等你发现时，已经积累了三个月垃圾。

软件工程早就解决过这个问题，办法叫 **CI**：每次改动都跑回归，退化立刻红灯。记忆系统没有这个东西。

## 2. 定位：EVO 在哪一格

### 2.1 市场分层

| 层 | 代表 | 载体 | 检索 | 审计 | 退化防护 |
|---|---|---|---|---|---|
| **L1 托管记忆 API** | Mem0、Supermemory、Memobase | 向量 + 图 + KV | 强 | 弱 | 无 |
| **L2 开源记忆框架** | Letta、Zep/Graphiti、LangMem、Cognee | 向量库 / 图库 | 强 | 中 | 无 |
| **L3 学术经验学习** | Reflexion、Voyager、ExpeL、A-MEM | 轨迹 + 技能库 | 弱 | 弱 | 无 |
| **L4 纯文件记忆** | Cline Memory Bank、`CLAUDE.md`、`MEMORY.md` | Markdown | 无 | 中 | 无 |
| **L5 可审计确定性账本** | **EVO** | 明文表格 + 索引 | 中 | **强** | **有** |

### 2.2 二维坐标

```
语义召回能力
   高 │   ●Zep      ●Mem0              ☆ 空位
      │            ●LangMem               强语义 × 强审计
      │  ●Basic Memory
      │
      │ ●Cline MB
   低 │ ●CLAUDE.md              ●EVO
      └──────────────────────────────────────→ 可审计性
            低                          高
```

EVO 在右下：**审计满格，语义中等**。

右上角是空的。这不是营销话术 —— 2026 年的行业选型综述自己写了一句："**推理记忆（决策链）这一层被严重低估，它决定了 Agent 的决策是否可解释、可审计**"。

EVO 的 `refs/`（推理层）+ 失败归因 + 硬约束表，已经在那格里。行业还在讨论这层要不要做。

### 2.3 EVO 不是什么

明确划界，避免误读：

- **不是**向量数据库，**不装** embedding 模型
- **不是**记忆 API，**不提供**多租户服务
- **不是**自动提取器，**不替**你决定该记什么
- **不是**通用框架，**不解决**业务问题
- **不是**产品，是一个**元流程**：从任务中学习

## 3. 架构

### 3.1 目录即架构

```
EVO/
├── SKILL.md              # 常驻规则：硬约束 H 总表、ROUTE 速查、F 公式索引
├── bin/evo               # 唯一入口（33 个子命令）
├── lib/                  # 检索与账本算法（公开）
├── refs/                 # 分卷规范：问题出现时才读
├── templates/            # 条目模板
└── data/
    ├── cmd/              # 34 个工具脚本（check / adv / eval / pack ...）
    ├── playbook/         # 枚举轨 + 语义域轨
    ├── journal.md        # 账本：人读视图
    ├── index.tsv         # 索引：检索视图
    └── store/            # 结构化视图（三元一致）
```

**没有数据库，没有服务，没有守护进程。** 一个目录拷走就是完整迁移。

### 3.2 四阶段循环

```
ROUTE ──→ EXECUTE ──→ REFLECT ──→ WRITE
  │          │            │           │
按需检索     交付产物      验收判定     够格才落账
L0-L3 分级   真实输出验证  失败归因     可复用+已验证+结论明确
```

四个阶段里，只有 `WRITE` 是有门槛的。**这是整个设计的关键**：绝大多数记忆系统在 `WRITE` 上无条件放行。

### 3.3 ROUTE 分级：省的是上下文，不是能力

| 级别 | 场景 | 动作 |
|---|---|---|
| **L0** | 闲聊、单步事实 | 直接答，不检索、不记账 |
| **L1** | 常规任务 | 检索一次，命中就引用 |
| **L2** | 复杂 / 多步 / 改代码 | 检索 + 列步骤与验收标准 |
| **L3** | 高风险（不可逆、动权限、改线上） | 先要上下文，先给回滚方案 |

传统记忆系统每次任务都全量注入。EVO 先判断"这次需不需要记忆"，再决定注入多少。**上下文成本从常数变成变量。**

### 3.4 三视图账本

同一份数据，三个消费面：

| 视图 | 文件 | 读者 | 用途 |
|---|---|---|---|
| 人读 | `data/journal.md` | 人 / Agent 正文 | 完整上下文、归因原话 |
| 检索 | `data/index.tsv` | `lib/search.sh` | 标题、别名、触发词 |
| 结构 | `data/store/` | `check.sh` | 三元一致性校验 |

**三方必须一致**（当前 63 / 63 / 63）。任何一方漂移，`evo check` 直接红灯。

这是 EVO 与"一堆 Markdown 文件"的根本区别：Cline Memory Bank 只有人读视图，`CLAUDE.md` 只有人读视图。**它们没有索引，所以不能检索；没有结构化视图，所以不能校验。**

### 3.5 检索层：双路

| 路径 | 实现 | 成本 | 能力 |
|---|---|---|---|
| **本地词面** | mawk 2-gram + 别名 + 触发词加权 | 0 token / 201~324ms | 精确、确定、可复现 |
| **平台向量** | 宿主 `query_memory` | 有 token 成本 | 语义、模糊、跨表述 |

**先词面，MISS 再上语义。** 词面能解决的不用向量，因为向量不可复现。

#### 中文 2-gram 的由来

v0.21 之前，中文检索基本是废的：

```
query:  中文长句查询老是搜不到
分词:   [中文长句查询老是搜不到]   ← 整句当一个词
匹配:   中文无空格，子串匹配必然失败
```

把查询按空格切分，中文整句就是一个"词"。英文 query 靠一个 `COUNT` 就能命中，中文全灭。实测 20 题真实问法集 **17 题 MISS**。

修法利用了一个 mawk 特性：`length` / `substr` 按**字节**操作，汉字 3 字节一字。于是每 3 字节一步、取 6 字节 = 2 个汉字：

```awk
for (p = 1; p + 5 <= ln; p += 3)      # 3 字节一步 = 一个字
    bg = substr(q2, p, 6)             # 6 字节 = 两个字
    if (bg ~ /^[\040-\176]+$/) continue  # 纯 ASCII 切片是乱码，跳过
    BIG[++bn] = bg
```

打分时 bigram 命中权重低于整词（标题 18 / 别名 12 / 触发词 8 / 结论 4），且**不并入整词计数** —— 两者量纲不同，混算会互相稀释。覆盖度分母用 `(hits + bh) / (n + bn)`。

结果：**Top-1 从 2/19 升到 17/20，MRR 从 0.1053 升到 0.8812，MISS 从 17 降到 1。**

### 3.6 门禁层：三级

| 级 | 命令 | 覆盖面 | 当前 |
|---|---|---|---|
| **L1 结构** | `evo check` | 账本格式、三元一致、引用完整性、版本漂移 | **19 项，全绿** |
| **L2 自检** | `evo self-test` | 工具脚本行为断言 | **41 条，41/0/0** |
| **L3 对抗** | `evo adv` | 检索/解析/边界攻击用例 | **32 用例 / 36 断言** |

这三级对应软件工程的：lint → unit test → fuzzing。

**记忆系统没有理由比代码标准更低。** 代码退化会报错，记忆退化不会 —— 所以记忆更需要门禁。

### 3.7 基准层：双集

`data/search-evalset.tsv`（真实问法 20 题）+ `data/search-evalset-simple.tsv`（关键词回归 20 题）。

**两集必须同时跑。** 只优化前者会让关键词检索退化，只看后者则看不见真缺陷。

这里踩过一个坑，值得写进白皮书当反面教材：

> 第一版用例是照着期望条目的标题特征词拼的 —— **基线 20/20，MRR 1.0**。
>
> 满分基线零信息量。任何优化都测不出差别，等于白干。
>
> 重写成自然语言问句（不含标题词、不含编号）后，基线掉到 **2/19**，真缺陷才浮出来。

**一个测不出缺陷的基准，比没有基准更危险** —— 它给你虚假的安全感。

## 4. 六个关键决策

每条都是"选了什么 / 放弃了什么 / 为什么"。这部分是本项目最核心的工程判断，也是别人最容易抄错的地方。

### D1 零依赖，不用 Python

**选择**：POSIX sh + mawk
**放弃**：Python 生态、现成的 NLP 库、数字处理能力
**理由**：

- 能跑在手机上（本项目实际运行在 Android 上的 Operit 平台）
- 能跑在 air-gapped 内网、路由器、CI 容器、任何有 `sh` 的地方
- 启动开销 0，没有 `pip install`、没有虚拟环境、没有版本冲突
- 十年后还能跑 —— 没有依赖腐烂问题

**代价**：mawk 没有数组排序、没有 Unicode 支持、字符串处理全靠字节。中文分词的 `substr` 技巧就是被逼出来的。

### D2 明文表格，不用向量库

**选择**：Markdown 表格 + TSV
**放弃**：embedding、相似度检索、语义泛化
**理由**：

- **可 diff**：账本可以 `git diff`，向量库不行
- **可审计**：审计员能读，embedding 不能
- **可迁移**：拷目录就走
- **可复现**：同样的查询必然返回同样的结果

**代价**：语义能力弱。两条已知失败的查询都是**词面断裂**（见 §7.1），词面检索修不了。

### D3 写入靠纪律，不做自动提取

**选择**：硬约束 + 七查门禁，Agent 必须显式判断"够格才写"
**放弃**：后台自动抽取、LLM 决定记什么
**理由**：

这是**最反直觉、也最重要**的一条。

- 自动提取 = 记忆内容由模型自由裁量 = **不可复现**
- 不可复现 = **审计价值归零**
- 审计价值归零 = EVO 存在的唯一理由消失

所以写入是**有门槛的**：只有同时满足「可复用 + 已验证 + 结论明确」才落账。不满足就不写，宁缺毋滥。

**代价**：维护成本高，对使用者有纪律要求。这是设计选择，不是缺陷。

### D4 bigram，不引入分词词典

**选择**：2 字切片 + 权重衰减
**放弃**：jieba 之类的分词、词典、词性标注
**理由**：引入词典就引入依赖，引入依赖就破坏 D1；词典本身也要维护，又是一份会腐烂的数据。

2-gram 是零成本近似：不需要知道词边界，也能让"长句"和"短句"产生重叠。

**代价**：精度低于真分词，会出现碎片匹配。用权重（18/12/8/4）压制。

### D5 门禁，不写"能跑就行"的脚本

**选择**：19 + 41 + 32 三道门
**放弃**：快速迭代、少写测试的自由
**理由**：记忆系统的失败是**静默**的。没有门禁，你不知道自己是变好了还是变坏了 —— v0.21 之前，这个项目的检索层**从来没有被评测过**，因为它看起来一直在工作。

### D6 基准先行，不凭感觉优化

**选择**：改评分函数前必须先建评测集
**放弃**：直接调参数试效果
**理由**：没有基准的优化等于随机漫步。v0.21 的评测脚本第一版自己就有 bug（`--all` 参数位置），同一道题两次跑出 15/20 和 17/20 两个数 —— 靠这个差异才抓到。

## 5. 实测数据

### 5.1 检索（v0.21）

| 用例集 | 优化前 | 优化后 |
|---|---|---|
| **真实问法** 20 题 | Top-1 **2/19**，MRR **0.1053**，MISS **17** | Top-1 **17/20**，MRR **0.8812**，MISS **1** |
| **关键词回归** 20 题 | 20/20 | **20/20（不退化）** |
| **公开样例集** 10 题（seed 账本，随仓库发布） | — | Top-1 **8/10** · Top-3 **9/10** · MRR **0.8500** |

### 5.2 延迟与成本

| 指标 | 值 |
|---|---|
| 短查询检索 | ~201 ms |
| 600 字长词检索 | ~324 ms（64 字节词长截断兜底，只产生 21 个 bigram） |
| 检索 token 成本 | **0** |
| 注入账本条目 | 按 ROUTE 分级，非全量 |

### 5.3 账本规模与一致性

```
账本条目       63
journal / index / store   63 / 63 / 63（三方一致）
check        19/19 通过
self-test    41 通过 / 0 失败 / 0 跳过
adv          32 用例 / 36 断言 全绿
bundle       216,266 B
```

### 5.4 口径声明（必读）

**上面所有数字都是「自有账本口径」，不是公开基准。**

- 我们没有跑过 LOCOMO / LongMemEval
- 我们的基线是 63 条真实条目 + 20 题真实问法
- 与 Mem0 / Zep 的规模差 4~5 个数量级

**谁要是拿「EVO 真实集 17/20」去对标「Mem0 LOCOMO 66.9%」，那是在制造一个不存在的比较。** 我们的基准只证明一件事：**改动没有让检索变差，或者让检索变好** —— 这是内部回归基准，不是对外性能宣称。

### 5.5 怎么验证

```sh
sh bin/evo check          # 19 项结构检查
sh bin/evo self-test      # 41 条断言
sh bin/evo adv            # 32 条对抗用例

sh bin/evo search-eval base            # 关键词集基线
sh bin/evo search-eval v021 real       # 真实问法集

sh bin/evo search '账本写入的规范是什么'
sh bin/evo search '心跳文件是零字节'
```

**逐字可复现（clone 下来就能跑）**

```sh
cp data/journal.seed.md data/journal.md
export EVO_JOURNAL="$PWD/data/journal.md"
sh bin/evo store sync && sh bin/evo index build
sh bin/evo search-eval example     # → Top1 8/10 · MRR 0.8500
sh bin/evo self-test               # → PASS=37 FAIL=0 WARN=3
```

**不可复现（需本机账本）**

| 项 | 原因 |
|---|---|
| §5.1 前两行（真实问法 / 关键词） | 用例集含本机条目标题，属判据层，不随仓库发布 |
| `check` 的 C6/C7/C9/C13 | 依赖账本真身、备份目录、结构报告 |
| `adv` 的多数用例 | 期望值绑定具体账本条目（如 `hits=3/3`） |
| `self-test` 的 41/0/0 | 公开仓库无账本、无 git → 3 条降级 WARN，得 37/0/3 |

**为什么不全公开**：评测集是判据层的核心资产（见 §9）。公开的是**框架 + 10 题样例 + 10 条 seed** —— 够你验证「这套机制真在跑」，但抄不走判据。

## 6. 与现有方案对比

### 6.1 十项指标

| 维度 | Mem0 | Zep/Graphiti | Letta | LangMem | Cline MB | **EVO** |
|---|---|---|---|---|---|---|
| 运行依赖 | Python/Node + 云 | 图库 | Postgres | LangGraph | 零 | **零（mawk/shell）** |
| 可离线 / air-gap | 否 | 否 | 否 | 否 | 是 | **是** |
| 检索机制 | embedding + 图 + KV | 时序图 + 语义 | 语义 + 分层 | 语义 | **无** | 词面 2-gram + 别名 + 平台向量 |
| 写入控制 | 后台自动提取 | 事实抽取 | 显式 block | 需自配 | 全量覆盖 | **硬必填 + 七查** |
| 矛盾处理 | 覆盖 + 摘要 | **valid_at/invalid_at** | 版本化 | 自配 | 人工 | supersede 失效标记 |
| 可审计 | 检索不透明 | 图谱可查 | git 版本化 | 弱 | 明文 | **明文 + 七查 + git + bundle** |
| 可复现 | 否 | 否 | 中 | 否 | 是 | **是** |
| 退化防护 | 无 | 无 | 无 | 无 | 无 | **19 / 41 / 32** |
| 基准 | LOCOMO / LongMemEval | DMR / LongMemEval | 自报 | 无 | 无 | 自有账本口径双集 |
| 检索 token 成本 | 极低 | 低 | 低 | 中 | 全量注入 | **0** |

最后三行（可复现 / 退化防护 / 基准），五个竞品全是空的。

### 6.2 行业数字（转引，未独立复现）

| 方案 | 指标 |
|---|---|
| Mem0 | LOCOMO **66.9%** @ **0.71 s** |
| 全量上下文基线 | LOCOMO **72.9%** @ **9.87 s** |
| Mem0 | LongMemEval **49.0%** |

> 来源：AIEng Hub《Agent 长期记忆 2026》2026-08，转引的独立评测。**本文未独立复现，仅作参照。**

关键不是 66.9%，而是 **14 倍延迟换 5.9 个点准确率**。这说明检索式记忆是正确的取舍 —— EVO 走同一条路（本地检索 201~324 ms，0 token），只是把检索器从 embedding 换成了词面 bigram。

### 6.3 不打谁

EVO 不打算取代上面任何一个。

- 要语义能力 → 用 Mem0 / Zep
- 要企业级运维 → 用 Letta
- 要 LangChain 集成 → 用 LangMem
- 要零依赖起步 → Cline MB 就够，但**一旦你开始在意"记忆质量"，它就到顶了**

EVO 的适用场景是：**你的记忆已经开始腐烂，而你不知道烂在哪。**

## 7. 已知边界

白皮书不写"局限"是耍流氓。这一节是 EVO 目前**做不到**的事。

### 7.1 两条已知 MISS（词面检索的硬上限）

| 查询 | 期望条目里的措辞 | 为什么救不了 |
|---|---|---|
| `提交前要跑哪些检查` | "收尾 sync → index → **七查**" | 与口语「提交/检查」**无词面重叠** |
| `中文长句查询老是搜不到` | "必然 **MISS**" | 跨表述，词面零重叠 |

这两条是**语义检索**的活，该走平台向量。词面检索假装能做词义映射，只会引入噪声。

**结论：不修，记档。** 这是 D2 的必然代价。

### 7.2 规模未验证

当前 63 条。`index.tsv` 是线性扫描，**500 / 1000 / 2000 条没压测过**。这是当前最大的未知数。

### 7.3 单机单用户

无并发、无多租户、无权限模型。**架构上不服务 B2B SaaS。**

### 7.4 写入靠纪律

没有自动提取，意味着使用者必须理解"什么值得记"。对不读文档的人是负体验。

### 7.5 无 SDK / 无 API

无法嵌入别人的产品。它是给人（和给 Agent）用的，不是给程序调的。

### 7.6 无公开标准集

无法对外宣称"比某某准确率高"。这是刻意的克制，不是能力不足。

## 9. 许可

**代码与规范**：AGPL-3.0-or-later
可自由使用、修改、分发。若将衍生作品作为网络服务提供，须以同许可开放源代码。

**判据层**（`data/` 下的评测集、门禁规则、对抗用例）：另有商业授权，不随 AGPL 授权。

**为什么是 AGPL 而不是 MIT**

这不是"假开源"。EVO 的核心价值不在代码（2-gram 检索约 100 行，谁都能写），而在**判据的积累** —— 那 32 条对抗用例是踩坑踩出来的，不是设计出来的。

MIT 意味着任何云厂商可以把它包成 SaaS 白嫖，且不回馈。AGPL 保留了这条路要谈授权的可能。

**商业授权**：见 `data/COMMERCIAL.md`（需申请）。
