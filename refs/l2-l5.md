# refs · 能力图谱 + L2~L5

> 自 SKILL.md v1.0.0 主干拆出（v1.0.1 上下文瘦身），内容原样保留、未改写。

## 能力图谱

维护多条平台记忆，标题格式 `能力图谱:<领域>`（如 `能力图谱:Android逆向` / `能力图谱:ROUTE检索命中统计`），按领域记录三字段：

- `level`：beginner / intermediate / advanced / expert
- `evidence`：支撑等级的证据（做过哪些任务、结果如何）
- `limits`：已知边界与不足

每完成一个新类型任务后更新对应领域（模板见 `templates/capability-map.md`）。

## L2 · 技能自进化

### 技能匹配（ROUTE 时同步做）

1. 列出技能库目录（`<Operit skills 目录>/`）下现有技能。
2. 按 frontmatter description 匹配当前任务；命中则按该技能流程执行。
3. 无匹配 → 正常执行，同时在 EXECUTE 中记录可复用流程，为生成做素材积累。

### 技能生成（满足任一条件即触发）

- 同主题规则积累 ≥3 条。
- 同一类型任务成功完成 ≥3 次。

流程：

1. 复制 `templates/skill-proposal.md` 填写提案。
2. 提案提交给用户确认；用户未反对即可执行固化。
3. 在技能库目录创建 `<skill-name>/SKILL.md`（frontmatter 含 name/description，name 不得与现有技能重名）。
4. 用一次真实任务验证：通过 → 启用；失败 → 修复后重试，最多 2 次，仍失败则放弃并记录原因。

### 退化检测与修复（每次 EVOLVE 时检查）

数据源：`技能统计` 记忆。

- 某技能使用 ≥3 次且成功率 <30% → 标记 `[退化]`，分析失败原因并修复该技能 SKILL.md。
- 修复后重新验证；连续 2 次修复仍 <30% → 归档（改名 `<skill-name>-archived`，不再挂载）。
- **禁止修改EVO自身**；退化修复只针对 AI 自建的业务技能。

### 近似合并

- 两个技能 name 或 description 语义相似且场景重叠 → 合并为一个：保留成功率高者，吸收另一方的独有步骤。

## L3 · 记忆库治理

### 膨胀控制（H8 硬性）

- 经验类记忆总量上限 100 条（v0.11 扩容，原 50；统计口径：self-evo 文件夹内 `经验:` 前缀条目；全量枚举路径见 H21）。
- 超限时按 EVOLVE 规则强制合并至 ≤60 条（原 30）。合并规程细则（v0.8，v0.10 补失败经验例外，v0.15 拆出）：见 `data/playbook/playbook-merge.md`（同场景成功率排序保留主条目 / 计数并入 / 失败经验独立配额例外 / delete + journal / H5 回读验证）。
- 连续 60 天未被命中且非规则类 → 归档删除。
- **journal 60 天截断（v0.11 定稿，v0.12 整文件轮转，v0.15 脚本化；12 月底首批到期）**：动作序列细则见 `data/playbook/playbook-truncate.md`；执行 = `sh bin/evo rotate-journal`（T-7 备份核对 + T0 交叉比对是脚本前置，必须人工确认后跑）。
- 游戏/检测对抗类经验标记「时效敏感」：淘汰窗口从 60 天缩至 30 天；条件变化时可改标续期。
- 归档区条目（如「归档:已终止项目」）不属于 self-evo 管理范围，不参与计数与淘汰。

### 备份双轨制（H17/H18 硬性）

细则（触发信号 / 双轨动作 / 恢复演练 / 备份范围）见 `data/playbook/playbook-backup.md`。核心不变：清单级快照 `manifest-YYYYMMDD.txt` + 全文级导出 `backup-YYYYMMDD-N.md`（~12 条/卷，逐卷 `create_file` 串行写入），落盘 `/sdcard/Download/self-evo-backup/`，双轨同时执行；v0.15 起触发信号化（F 表 H17 行），完成后 journal 追加 `backup` 行含触发原因。

### 派生索引（H15 硬性）

- 索引条目（`索引:<项目>`）的内容一律由入库动作按 tags 自动派生，禁止手写维护清单。
- 新经验 tags 不属于任何现有「索引:*」→ 由入库动作新建「索引:<项目>」条目（v0.8：建索引本身也是入库动作，不算手写维护）。
- 手写索引腐坏是已实证教训（65 条全量盘点修复），此后索引只允许"入库时 append + 定期一致性校验"，不允许手工编辑。

### 记忆链接维护（v0.16 新增，第三档）

- 链接层职责：维护五层 schema 条目之间的语义链接（经验↔事件↔规则↔项目状态↔机制），工具为 `extended_memory_tools:link_memories` / `query_memory_links` / `delete_memory_link`。
- **写入义务**：新经验入库时若其结论直接支撑某事件/规则，创建 `INVOLVES` / `DERIVED_FROM` 链接（新链接类型一律大写：INVOLVES / DERIVED_FROM / UPDATES / FOLLOWS / CORRECTS / APPLIES_TO / PART_OF；历史小写类型不追溯改名）。
- **delete 义务**：delete 条目后检查指向该条目的链接（query_memory_links 过滤 target/source），残留链接一并删除；平台级联删除失效时按 link_id 补删。
- **噪音检查**：自链接（source=target）一律删除；autoDream 索引校验时顺带抽查新增链接的自链接率。
- **克制原则**：链接不是越多越好——只建「引用关系」和「提炼关系」，不建「同主题相关」这种弱关联；补链接前先 query_memory_links 查重，避免重复链接。

### 检索评测集（v0.16 新增，第二档）

- 文件 `data/retrieval-evalset.md`：20 个真实历史任务问题 + 期望命中精确标题，为检索策略回归基线。
- **执行义务**：任何 threshold / folder_path / 关键词检索策略调整前后，必须先跑评测集对比命中数，只升不降才允许上线；跑法见评测集文件头部说明。
- **首跑基线**：18/20 = 90%（2026-11-09 UTC）；未命中 Q12/Q13 归因「通用词被事件类条目挤占 limit 窗口」记录在案，下次策略调整优先验证这两题。
- 新经验入库导致旧问题答案变更（合并/失效）→ 同步更新评测集期望标题（评测集文件维护义务第 1 条）。

### 单一权威表（v0.12，堵 11-09 双写漏事故复发）

每个数据项只允许一个权威位置 + 明确镜像；双写义务收口到本表。任何批次动作先查本表：动了权威 → 必动镜像；禁止只写镜像不写权威。

| 数据项 | 权威位置 | 镜像位置 |
|---|---|---|
| last_dream / complete / alarm_landed | 「时钟:autoDream」条目 | waters.md（镜像，v0.15 起由权威回读重生成，非双写动作） |
| 跨对话采集水位 | 「自进化状态」条目 | waters.md（镜像，回读重生成） |
| 补采账 | 「自进化状态」挂账段 | waters.md 补采账段（同格式，回读重生成） |
| 条目计数 | H21 三口径枚举 enum-total 实时结果（wc -l / grep -c 命令计数，唯一权威，不递推不存档） | 自进化状态（仅快照记录） |
| journal 变更流水 | data/journal.md | 无镜像（H14 仅审计） |
| 技能/版本状态 | 「自进化状态」条目 | 无镜像 |

11-09 教训：13:10 优化轮只更新「自进化状态」漏 waters/时钟镜像——双写义务无权威声明时每次双写都是赌博，本表即制度解。v0.15 升级：waters 从「双写义务」降为「回读重生成」——只写权威（记忆条目），waters 内容由 `get_memory_by_title` 回读权威后重生成；回读失败 → 保留旧 waters 并在 journal 挂账「waters重建失败」。

### 改动节奏纪律（H23 硬性，v0.14 新增）

1. 任何版本改完，至少满足其一才能开下一版本：跑满 10 个真实任务，或观察满 24 小时。
2. 观察期内发现的问题，记入 journal 的「待修」区，不立刻改；攒到观察期结束统一改。
3. 版本号后缀区分：`-dev`（改完未过观察期）、`-stable`（已过观察期）。当前 v0.15 标 `-dev`（跳过观察期理由见版本链注释）。
4. 违反本条（未过观察期就开下一版）需在 VERSION_HISTORY 该版条目内写明「跳过观察期」及理由。

## L4 · 夜间整合（autoDream）

**触发（双通道，任一满足即执行）**：

1. 被动通道（v0.10.4 放宽）：每条消息轻量检查——查「时钟:autoDream」条目的 `last_dream` 时间（只读 ~200B，成本可忽略）；距今 >24h 则执行整合。不再依赖「每天首条消息」判定（长会话中首条消息可能恰为闲聊导致漏触发）。
2. 主动通道：宿主用 daily_life 包 `schedule_one_time_task` 配置每日 03:00 唤醒本对话执行整合——对话静默时也能触发；每次唤醒执行整合后，**顺带重配次日 03:00 唤醒**（自续链）。
3. 兜底：查不到 `last_dream` 字段 → 视为已超 24h，立即执行。
4. 时钟载体（H16/T2，v0.8）：`last_dream` 与执行完成标记的权威值放轻量条目「时钟:autoDream」，waters.md 为镜像（v0.15 起回读重生成）；每次检查只读时钟条目（~200B），不再读「自进化状态」全文。「自进化状态」的 last_dream 字段只作历史记录。
5. 回写义务（H10 硬性）：每次执行整合完成后，必须回写「时钟:autoDream」的 `last_dream` = 当前时间 + `complete: true`；不回写 = 未完成。
6. 执行完成标记（H16 硬性）：若整合执行到一半被打断，回写时挂 `complete: false` 及断点位置（stage 名）；下轮启动先查时钟条目该标记，命中则自动从断点 stage 续跑，不再等人工问询。

**手动触发**：用户说「检测真实数据」「查看收集的数据」「数据检查」等同义指令 → 立即执行一次整合（即使未超 24h），等价于 autoDream。

六阶段：

1. **扫描**（v0.8 数据源绑定，v0.12 补冗余窗口与去重）：`query_memory(folder_path="self-evo", start_time=last_dream-1h, limit=50)` 收集新增/更新条目（-1h 冗余窗口兜住整合期间创建时间戳早于 last_dream 的条目），辅以 `data/journal.md` 读同窗口变更行交叉核对；Source unknown 平台自动捕获条目与库内已有条目比对，内容重复者挂账忽略、不重复计数不重复沉淀；数据源不靠猜。
2. **归类**：按主题聚类（同场景归一组）。
3. **提炼**：每组经验 ≥3 条 → 提取规则候选并升级。
4. **增强**：技能统计中成功率高且使用多的技能 → 补充细节、边界与更优步骤。
5. **弱化**：使用少且成功率低的技能 → 简化或标记 `[待归档]`。
6. **差距**（v0.12 衔接 L2）：能力图谱 limits 中"想做但没做过"的领域若已积累 ≥3 条相关经验 → 按 `templates/skill-proposal.md` 产出提案 → 走 L2 技能生成流程第 2 步（用户确认）；两套触发（limits ≥3 条 / 规则 ≥3 条）产出物统一为提案模板，不再各自散写。
7. **简报**（v0.16 新增，第三档）：整合完成后生成一段人话摘要（≤200 字），写入「自进化状态」条目整合日志的「简报」段——格式：`简报:<日期>: <一句结论> + <今天新增/合并/失效/风险各几条>`。次日首条用户消息时若简报未读，在回复开头附上（一句带过，不打断主线任务）。简报只产出结论不产出过程日志。

挂账清账（接在六阶段后，优先执行）：

1. P0 pending 区待写条目与 L5 补采账优先重试写入。
2. 清账结果写进 `自进化状态` 整合日志（时间 + 动作 + 前后值）。

执行约束：

- 单次整合保持轻量，结论只写进 `自进化状态` 记忆，不另建散落条目。
- 不修改EVO自身文件。
- 任何校准/修正动作必须写入 `自进化状态` 的整合日志（时间 + 动作 + 前后值），保证数据变更可溯。

## L5 · 跨对话采集水位协议（v0.6 实弹验证）

职责：从宿主平台其他对话持续采集增量，提炼入库。工具：`extended_chat:list_chats`（水位对比）、`extended_chat:read_messages_range`（区间读取）。

### 水位推进硬条件（H11，漏采教训：83→134 只读最新 20 条 → v10 段漏采）

1. 水位只有在「从旧水位连续读到最新」成立时才允许推进。
2. 区间读取：`read_messages_range(chat_id, 旧水位, 当前总数)` 逐段读，段长 30~50；禁止用固定 limit 只看尾部。
3. 中间段缺失/读取失败 → **水位不推进**，在 `自进化状态` 挂补采账 `补采:<对话>:<区间>`（权威在自进化状态条目；waters.md 补采账段由回读重生成，格式：`补采:<对话>:<区间> | 挂账时间`，v0.8 定格式），夜间整合优先清账。
4. 增量分档（H12，省 token）：增量 ≤5 条 → 只更新水位与 updatedAt，不读正文；6~50 → 全量读；>50 → 分页循环。
5. 水位推进后：更新「自进化状态」权威条目 → `get_memory_by_title` 回读 → 重生成 `data/waters.md` 对应段（v0.15 镜像化，取消双写动作；回读失败保留旧 waters + journal 挂账）。
